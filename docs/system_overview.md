# システム概要

この文書は現在のコード構成と運用上の制約を説明します。実測していない削減率や、実機で確認していない動作を完了事項として扱いません。

## 処理の流れ

```text
Cloudflare Cron（2分間隔）
  -> BWF Match Centreから大会・試合を取得
  -> 日本人選手の試合を抽出・正規化
  -> H2Hを解決
  -> 変更時または30分経過時だけ試合状態をKVへ保存
  -> 新しくライブになった試合を購読者へ通知

ブラウザ
  -> /api/statusで保存済み状態を2分間隔で取得
  -> ライブ試合がある間だけ/api/liveを15秒間隔で取得
  -> 非表示または5分無操作で取得を停止
```

## 外部呼び出しの一覧

コード（2026-11-06時点）から読み取った呼び出し元・呼び出し先・頻度です。`T` は「BWFの開催中大会一覧に載る大会数＋`config/match-center-tournaments.json` で補完した大会数」で、日本人選手が出ていない大会も含みます。

### 1. Cron（2分ごと、1日720回）: `runNotificationCheck`

| 呼び出し先 | 1回あたり | キャッシュ | 備考 |
|---|---|---|---|
| KV get `push:state` | 1 | なし | 前回状態の読み込み |
| BWF 開催中大会一覧 `vue-current-live` | 1 | なし | 失敗時は別ヘッダーで1回再試行 |
| BWF 日別試合 `day-matches` | T × 3日 | なし | 前日・当日・翌日。失敗時は再試行 |
| KV get `bwf:h2h:v3:<試合ID>` | H2H未取得の試合数 | — | 前回状態にH2Hがある試合は読まない |
| BWF H2H `h2h/statistics` | 上と同じ | KV | 取得できたら30日保存。成績が返らなかった場合は6時間、通信エラーは1時間「取得できなかった」と記録し、その間は問い合わせない |
| BWF 日別試合（履歴） | 12時間に1回だけ T × 7日 | Cloudflare 12時間 | 直近7日の結果の補完 |
| KV put `push:state` | 状態が変わったとき、または30分ごと | — | 変化がなければ書かない |
| KV list `push:subscription:*` と Web Push 送信 | 新しくライブになった試合があるときだけ | — | 購読者数 × 対象試合数を送信 |

### 2. 画面（ブラウザ）: `src/frontend/lib/matchesState.ts`

画面が表示されていて、5分以内に操作がある間だけ動きます。非表示または5分無操作で止まり、戻ったときに1回取り直します。

| 呼び出し先 | 頻度 | 条件 |
|---|---|---|
| `/api/status` | 2分ごと＋表示復帰時＋再読み込みボタン | 常に |
| `/api/live` | 15秒ごと | ライブ中の試合があるときだけ |
| `/api/config` | 起動時1回 | 通知設定の初期化 |
| `/api/subscriptions*` | 利用者の操作時だけ | 通知のオン・オフ、試合ごとの除外、テスト通知 |
| `/api/media` | 画像ごとに1回（ブラウザが7日保持） | 画面内に入った画像だけ（lazy） |

### 3. Worker API: `src/api/app.ts`

| API | Worker側の処理 | キャッシュ |
|---|---|---|
| `/api/status` | KV get `push:state` 1回 | Cloudflareのデータセンターごとに30秒。利用者数が増えてもKV読み取りは増えない |
| `/api/live` | **Cronと同じ全件取得**（BWF 1 + T × 3日） | データセンターごとに10秒。BWFへの各リクエストもCloudflareで10秒保持 |
| `/api/media` | BWF画像を1枚取得 | データセンターごとに7日。Worker経由のBWF取得は1枚約3〜4秒かかるため、取得済みの画像はエッジから返す（`X-BWF-Cache: HIT`） |
| `/api/subscriptions*` | KV get / put / delete 各1回程度 | なし |

### 既知の課題

- `/api/live` は、ライブ得点だけが必要なのに、Cronと同じ全大会×3日分の取得をしています。画面を見ている人がいるデータセンターでは、10秒ごとに最大 1 + 3T 件のBWFリクエストが発生します。
- H2Hが取得できない試合は、以前は2分ごとにBWFへ問い合わせ直していました（2026-11-06の公開データで予定試合3件、1日あたり約2,160回）。現在は「取得できなかった」ことをKVへ記録して問い合わせを止めています。KVの読み取りは2分ごとに1試合1回残ります。
- Cronの日別試合取得はCloudflareキャッシュを使わないため、毎回BWFへ届きます。

## 責務

### フロントエンド

- `src/frontend/components/`: 表示と操作
  - `Matches.tsx`: タブ、並び替え、試合カード、H2H
  - `RecentResults.tsx`: 直近7日間の試合結果
  - `Schedule.tsx`: 今後の大会の一覧・カレンダー・詳細
  - `Notifications.tsx`: 通知設定とインストール・許可の案内
状態モジュール（`matchesState.ts`、`pushNotificationState.ts`、`pwaInstallState.ts`）は読み取り関数と操作関数だけを公開し、状態の書き換え関数（setter）は外部へ公開しません。算出値は描画ルートの外で `createMemo` を作らず、通常の関数として公開します。

- `src/frontend/lib/matchesState.ts`: 試合状態と更新ライフサイクル
- `src/frontend/lib/pollingPolicy.ts`: 停止・通常・ライブ更新の純粋な判定
- `src/frontend/lib/pushNotificationState.ts`: Push購読と試合別除外設定
- `src/frontend/lib/matchList.ts`: 試合の並び替え、大会別グループ化、ライブ得点の反映
- `src/frontend/lib/calendar.ts`: 大会カレンダーの月・週・帯の計算（純粋関数）
- `src/frontend/lib/viewPanels.ts`: タブの中身の作成と表示切り替え。一度作ったタブは作り直さず隠すだけにし（`content-visibility: hidden`）、最初の画面を描いた後の空き時間に残りのタブも作っておく。結果タブは試合数が多く、切り替えのたびに作り直すと表示まで待たされるため。「ライブ」と「このあと」も別々の画面として持ち、行き来しても試合カードを作り直さない。隠したタブの配置も空き時間に計算しておき、初めて開いたときに待たせない
- `src/frontend/lib/stableItems.ts`: 定期更新で届いた一覧のうち、内容が変わっていない試合は前回のオブジェクトを使い回す。2分ごとの更新で、変わった試合のカードだけが描き直される
- 画面の操作では、できるだけカードや行を作り直さない。結果の「勝ち / 負け」の絞り込みは該当しない行を隠すだけにし、試合一覧の並び替えはカードと大会見出しを1本の並びにして順番だけを入れ替える
- `src/frontend/lib/format.ts`: 日付、ラウンド、コート、スコアの表示整形
- `src/frontend/lib/browser.ts`: 端末・ブラウザ判定と通知トグルの動作判定
- `src/frontend/lib/api.ts`, `media.ts`: API呼び出しと画像中継URL
- `src/frontend/pwa/sw.js`: オフラインキャッシュとPush表示

試合カードでは、ライブ状態または開始時刻、選手、得点を主情報とします。大会名、ラウンド、コート、H2H、前回対戦は補助情報です。日本人チームはAPI正規化時に先頭へ移動します。

### Worker API

- `src/api/app.ts`: HTTPルート、APIキャッシュ、Cronの入口
- `src/api/notificationCheck.ts`: Cronの定期処理（試合取得、通知対象の判定、KV保存の要否判定）
- `src/api/tournamentCalendar.ts`: 同梱した大会カレンダー設定の結合
- `src/api/bwf.ts`: BWFへのHTTP取得と処理の組み立て
- `src/api/bwfMatch.ts`: 試合状態判定と日本人試合の正規化
- `src/api/bwfH2h.ts`: H2H取得、キャッシュ、レスポンス解析
- `src/api/push.ts`: 購読保存、除外適用、Web Push送信
- `src/api/media.ts`: 許可したBWF画像の中継

外部レスポンスを扱う処理と、入力から結果を返す純粋処理を分けています。外部形式の変更は取得・解析側で吸収し、UIや通知処理へ未知の形式を渡しません。

BWFの現在開催中大会APIに掲載されない大会は、手動管理する `config/match-center-tournaments.json` の開催期間と大会コードで補完します。自動生成される `config/upcoming-tournaments.json` とは分離し、定期大会情報更新で試合取得設定が失われないようにします。API掲載分とコードが一致する場合は重複取得せず、開催期間に重なる大会だけを日別試合APIの取得対象にします。

## 通知契約

通知APIの型は `src/type/index.ts` でフロントエンドとWorkerが共有します。

- 購読登録: `{ subscription }`
- 除外更新: `{ endpoint, excludedMatchIds }`
- テスト通知: `{ endpoint }`

全試合の通知が既定で有効です。利用者が外した試合IDだけを購読レコードへ保存します。複数試合を同時に通知する場合、送信結果は試合単位で記録し、全送信が失敗した試合だけを最大3回まで再試行します。部分成功は、受信済み購読者への重複を避けるため再送しません。

## 保存とキャッシュ

KVには次のデータを保存します。

- 最新の試合状態と通知済み試合
- Push購読と試合別除外
- H2Hキャッシュ

大会カレンダーは同梱設定（`config/bwf-calendar-2026.json`、`config/upcoming-tournaments.json`）から `/api/status` が毎回組み立てるため、KVには保存しません。旧バージョンが保存した `upcomingTournaments` は読まずに無視し、次回の書き込みで消えます。

購読一覧はKVのlist結果に含まれるmetadataを利用します。metadataは送信に必要な値だけを短縮キーで保存し、JSON表現が[Cloudflareの1024バイト上限](https://developers.cloudflare.com/kv/platform/limits/)を超える場合はmetadataを付けず、送信時にそのレコードだけ個別getへフォールバックします。KVの利用量はCloudflare側のメトリクスで確認し、固定の削減率は文書上で保証しません。

## 画面デザインの基準

色・文字・余白は `src/frontend/app.css` 冒頭のデザイントークン（CSSカスタムプロパティ）だけを使います。値を直接書かず、トークンを追加・変更します。

- 文字サイズ: 12 / 13 / 15 / 18 / 22 / 32px の6段階。太さは 400 と 700 の2種類だけ（単体テストで検査）
- 太字は、日本人選手名・現在の得点・開始時刻・見出し・勝者・選択中の項目に限る
- 意味を持つ色は用途を固定する: アクセントの青は操作できる要素、赤はBWFロゴとライブ中、緑は勝ちと通知オン、灰色は負け
- 日本語は文節単位で折り返す（`word-break: auto-phrase`）。タブ・バッジ・ラベルは1行に固定する。長いカタカナの大会名だけは語中でも折り返す
- 選手名は1人1行。ダブルスのペアの間に「/」などの区切りは出さない（読み上げ用の区切りだけ残す）。文中でペアを1行に書くときは「・」でつなぐ
- 相手選手名は1行に収まらない分だけ省略し、レイアウトを広げない
- 日本人選手のためのサイトなので、表示は常に日本人選手を主役にする
  - 日本人選手のチームは左に置く（日本人対決は試合データの順）。試合カードでは欄全体に淡い黄色の背景（`--color-japan`）を敷く
  - 試合結果では、黄色の背景は勝った日本人選手の欄だけに敷く。負けた試合では敷かない
  - 試合結果は、カード上部の帯で日本人選手側の勝敗と取ったゲーム数を示す（「勝ち 2-0」緑 / 「負け 0-2」灰）。海外選手が勝っても印は付けない。日本人対決だけ、勝った側に「勝ち」の印を付ける
  - 対戦成績は日本人選手から見た「N勝M敗」で示す
  - 結果タブには日本人選手の勝敗の集計と「すべて / 勝ち / 負け」の絞り込み、日付ごとの勝敗数を出す
  - 結果タブの上部に、今日（日本時間）の日本人選手の成績を大会ごとに出す。その大会の今日の試合がすべて終わっていれば「◯勝◯敗」、終わっていなければ「残り◯試合」。周りと同じ文字の大きさ・太さにして目立たせすぎない
- チーム欄の写真・国旗・名前は中央にそろえる。各ゲームの得点は勝った側の数字だけを太字にする
- 影とグラデーションは使わず、区切りは1pxの線で表す

## 日本人選手名

BWFはローマ字表記（例: `Hina AKECHI`）で返すため、`src/config/japanese-player-names.ts` の辞書で漢字表記へ変換します。変換はCronがBWFから取得した時点で行うため、辞書を更新すると、現在の試合は次のCronで、KVに保存済みの直近の結果は次の履歴取得（12時間ごと）で反映されます。

辞書には、日本バドミントン協会の派遣・参加者名簿など公式資料で確認できた表記だけを追加します。名簿にはローマ字が無いため、同じ大会の名簿で種目とペアの組み合わせが一致すること、または姓が名簿内で1人だけであることを照合の根拠にします。

## 画像

選手写真、国旗、大会ロゴはBWFの画像配信（`img.bwfbadminton.com`）から `/api/media` 経由で表示します。画面側（`src/frontend/lib/media.ts`）でURLの `/image/upload/` 直後に縮小指定を加え、表示サイズに合った画像だけを取得します（選手写真は144px四方、国旗は幅96px、ロゴは幅112px）。画面外の画像は `loading="lazy"` で表示されるまで読み込みません。

公開中のデータで計測した結果、結果タブを開いた直後の画像通信はスマホで約15.2MBから約0.16MBへ、結果を最後まで見た場合でも約0.39MBへ減りました。

大会ヘッダー画像（`tournamentHeaderImageUrl`）は開催地の風景写真で大会を識別できず、1枚約0.9MBと重いため表示しません。

## PWA

本番ビルド時だけManifestとApple向けPWAメタデータをHTMLへ追加し、ハッシュ付きJS/CSSをService Workerのアプリシェルへ埋め込みます。本番通知では日本人選手写真を`image`と`icon`へ設定し、写真がない場合はアプリアイコンへフォールバックします。

開発時はPWAを完全に無効化します。5173ではManifestを追加せず、起動時に同一オリジンのService Worker登録とCache Storageを削除します。`/pwa/sw.js`へアクセスされても、キャッシュやPush処理を持たず自身を解除する移行用Workerだけを返します。

8787は`wrangler.dev.jsonc`と`src/api/development.ts`でAPI専用Workerとして起動し、`dist`の本番静的アセットを読みません。過去に8787へ登録された本番Service Workerを除去するため、API以外のルートは`Clear-Site-Data`付きの解除ページ、`/pwa/sw.js`は自身を解除するWorkerを返します。これにより、開発サーバー終了後にオフラインシェルだけがlocalhostへ残る状態を防ぎます。

OGP画像は `public/pwa/og-image.png` の1200x630画像です。HTMLの寸法指定と実ファイル寸法を単体テストで確認します。

## プレビュー

Pull Requestごとの確認には [Worker Previews](https://developers.cloudflare.com/workers/previews/) を使います。`main` 以外のブランチへのpushで Workers Builds が `npx wrangler preview` を実行し、Pull Requestのコメントにプレビューの URL を載せます（Wrangler 4.135.0 以上が必要）。

- プレビューは本番の設定を引き継がず、`wrangler.jsonc` の `previews` ブロックの設定で動きます
- 実データで画面を確認できるよう、プレビューは本番と同じKVを読みます。`APP_ENV=preview` のときは購読API（`/api/subscriptions*`）が403を返し、`/api/config` が `notificationsAvailable: false` を返すため、画面は「プレビューでは通知を使えません」と表示し、本番の購読データへは書き込みません
- Cron（2分ごとの定期処理）はプレビューでは動きません（Cloudflareの仕様）。プレビューの試合情報は、本番のCronがKVに保存したものです
- 本番で必須のシークレット（`VAPID_*`）は、ダッシュボードの Previews Base に別途設定します。プレビューでは通知を使わないため、値は本番と異なっていても構いません
- Version URL（`preview_urls`）は使わないため無効にしています

## 開発と検証

`bun run dev` はViteと開発API用Wranglerを同じ親プロセスで管理します。Worker起動後にscheduled処理を1回実行し、画面はlocalhost:5173、APIはlocalhost:8787で提供します。片方の異常終了またはCtrl+Cで両方を停止します。

`bun run precommit` は次を実行します。

1. Wrangler生成型の差分確認
2. TypeScript型検査
3. Biome
4. 単体テスト
5. Worker統合テスト
6. Playwrightレイアウト・更新遷移テスト
7. Playwright開発PWA解除テスト
8. Wrangler dry-run

GitHub Actionsでも同じコマンドを実行します。`main`へのpush後のデプロイはCloudflare側のパイプラインが担当します。

## 確認が必要な制約

- BWFの取得先は安定提供が保証された公開APIであることを確認できていません。形式変更をfixtureとログで検知する必要があります。
- iOSのWeb Pushはホーム画面へ追加したWebアプリから許可する必要があります。自動テストだけで実機配送を証明できないため、リリース前の実機確認対象です。
- KV metadataのサイズとlistページ数は購読数増加時に計測し、上限接近を監視する必要があります。
- `/api/live` は、エッジキャッシュが切れるたびに、Cron と同じ全件取得（大会数×3日分の日別試合API）を実行します。ライブ得点だけを軽く取得できるBWFの取得先があるかは、実レスポンスで確認できていないため未対応です。
- 公開API（`/api/status`、`/api/live`）には、画面で使っていない項目（`players`、大会ヘッダー画像URLなど）が含まれています。別リポジトリのCLIがこれらを使っているか確認できていないため、互換性のため残しています。
